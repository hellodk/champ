# Champ CLI — Headless Agent for a 16 GB Mac Mini Fleet

> **Status:** Design / proposal. No implementation has started.
> **Constraint:** A pool of Mac Minis, **16 GB unified memory each**. The CLI must
> make a local LLM win at long-horizon coding tasks within that budget.
> **Provenance labels:** **[V]** verified by reading the code in this repo,
> **[R]** from prior source research on aider/cline/opencode/pi (not re-verified
> in this doc), **[L]** external literature, **[derived]** arithmetic with stated
> assumptions.

---

## 1. Why this design looks the way it does

16 GB of unified memory is shared between CPU and GPU (Metal). Per machine, the
budget splits roughly as follows **[derived]**:

| Consumer | Cost |
|---|---|
| macOS + background services | ~4–6 GB |
| 4-bit model weights | 4B → ~2.5 GB · 8B → ~4.5 GB · 14B → ~8.5 GB |
| **Remaining for KV cache + activations** | **~5–9 GB** |

KV cache per token = `2 (K+V) × layers × kv_heads × head_dim × bytes`. For a 4–8B
GQA model (≈32–36 layers, 8 KV heads, head_dim 128, fp16) that is **≈128–144
KiB/token** → 8k context ≈ 1.1 GB, 32k ≈ 4.3 GB **[derived]**.

Three consequences drive every choice below:

1. **Working context is 8k–32k, not 128k.** Big-context habits — dumping whole
   files, optimistic windows, naive truncation — are self-defeating here.
2. **Prefill (compute) is the Metal bottleneck, not decode.** Rebuilding a prefix
   costs far more than reusing it → **KV-cache reuse is the single biggest win**
   **[L]**.
3. **Memory must be computed and reserved, not hoped for.** The fleet should
   standardise on 4B–8B models; a 14B model leaves almost no KV room.

**The CLI is a context-budgeting engine for small, slow-prefill models — not a
thin wrapper over a large-context API.**

## 2. Principles (convergent across the field)

| Principle | Backing |
|---|---|
| Context is a **budget** managed by compaction, not truncation | [R] aider (repo-map budget), cline (90% auto-compact), opencode/pi (checkpoint-bounded) |
| **Stable prefix + append-only** history to preserve the KV/prompt cache | [L] Manus (cache-hit rate = #1 metric; input:output ≈ 100:1), [L] Anthropic "Effective context engineering" |
| **Measure provider-reported tokens; estimate only the tail** | [R] cline (`CHARS_PER_TOKEN=3`), pi (`3.5`), opencode (measured + estimated) |
| **Truncate tool output at the boundary; spill to disk** | [R] pi `truncate.js` (2000 lines / 50 KB / 1 MiB spill) |
| **Shrink tool schemas to the task** | [R] pi BM25 tool-search + codemode (~3k token schema budget) |
| **Make everything lazy** | [R] opencode lazy ripgrep / lazy git snapshot; aider lazy repo map |
| Longer context ≠ better; accuracy degrades with length | [L] Chroma "context rot" / lost-in-the-middle |

## 3. Architecture — reuse the headless core, add a thin CLI

Verified **[V]**: `AgentController`, every file in `src/providers/`,
`src/tools/registry.ts`, `src/tools/types.ts`, `src/config/config-loader.ts`,
`src/memory/*`, and `src/server/champ-server.ts` contain **no `vscode` import**.
Only 7 tools are vscode-coupled. There is **no `src/cli.ts`** and no `bin` field;
esbuild has a single entry (`src/extension.ts`).

The work is therefore narrow:

```
┌──────────────────────────────────────────────┐
│  src/cli.ts  (new esbuild entry → bin)        │
│  REPL / one-shot / stdin-pipe modes           │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│  AgentController  (reused — already headless) │
│  Providers · ToolRegistry · Safety · Memory   │
│  MCP · Skills · Rules                         │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│  NEW: headless fs tools (fs-backed)           │
│  NEW: Context Engine (§4)                     │
│  NEW: persistent session store (§4 L2)        │
└───────────────────────────────────────────────┘
```

- **Headless tool layer** — port the 7 vscode-coupled tools (`read-file`,
  `edit-file`, `create-file`, `delete-file`, `list-directory`, `grep-search`,
  `file-search`) to an `fs`-backed implementation behind the existing
  `ToolRegistry` interface. `ToolCallingLoop` and `scripts/bench-agent.ts`
  already exercise this path headlessly **[R]**.
- **`src/cli.ts`** — second esbuild entry (`dist/cli.js`) + `bin` field + shebang.
- **Reuse `ChampServer`** for an optional headless HTTP mode.

## 4. The context engine

Six layers, each independently testable, each mapped to a ticket.

### L1 — Provider-anchored token accounting  *(new ticket)*
Today `ContextWindowManager.estimateTokens` sums `provider.countTokens` per
message **[V, `context-manager.ts:40-48`]**. Replace with: take the
**provider-reported** `prompt_tokens` from the last response as ground truth for
the prefix, and estimate only messages appended since; reconcile every turn. On
an 8k window a ±10% estimate error is a dropped tool call.

### L2 — Persistent, checkpointed session store  *(issue #72)*
History is in-memory today. `CheckpointManager` persists **file snapshots** only,
as JSON+base64 with atomic temp+rename, and still imports `vscode`
**[V, `checkpoint-manager.ts` / `checkpoint-store.ts`]**. Design: append-only
JSONL session log + `checkpoint` records keyed by sequence, so a resumed session
replays to the last checkpoint without re-summarising. Bound context *by
checkpoint*, matching [R] opencode/pi. Reuse `CheckpointStore`'s atomic-write
pattern; drop the `vscode` dependency.

### L3 — Pair-safe, persisted compaction  *(issue #114, items 1–2)*
`fitMessages` slices `rest.slice(0,-1)` then shifts the oldest — it can split an
assistant `tool_use` from its `tool_result` **[V, `context-manager.ts:56-81`]**,
which hard-errors Anthropic-style APIs. `fitWithSummary` re-summarises the full
history on **every** call and never persists the result **[V,
`context-manager.ts:88-161`]** → repeated summariser calls per iteration. Design:
(a) drop in **atomic groups** (assistant message + its tool_results);
(b) write the compaction back into the session store so later iterations reuse
it; (c) ordered degradation — drop thinking → drop media → truncate text → drop
groups **[R]** cline.

### L4 — Tool-result boundary control  *(issue #114, item 3)*
`ToolCallingLoop` pushes the **full** `result.output` into history
(`tool-calling-loop.ts:335`) while `truncateForMetrics` (`:47`, applied
`:306-309`) affects metrics only **[V]**. One large `read_file` blows a small
window; the loop also has `MAX_ITERATIONS = 4` and **no context fitting at all**
**[V]**. Design: a budget-aware accumulator that head+tails output with an
explicit `… [N chars elided → <spill file>]` marker, and fits before each append.

### L5 — Prompt / KV-cache discipline  *(new ticket)*
No prompt-cache concept exists today; `ResponseCache` is in-memory, TTL'd, keyed
on the full messages hash, never persisted **[V, `response-cache.ts`]**. Design:
byte-identical stable prefix (instructions + tool schemas first) across turns;
append-only turn log; explicit KV-checkpoint markers; warm only when it pays
(`expectedSavings = P(continuation) × missCost − warmCost`, warm if above a
threshold) **[R]** pi/aider. This is where the fleet wins most, because prefill is
the bottleneck.

### L6 — Tool-schema shrinking + retrieval  *(ties to #113 items 3–4)*
`getDefinitions()` sends every tool every turn **[V]**. Send a task-relevant
subset selected by BM25/embedding relevance within a schema-token budget [R] pi,
and upgrade the repo map to tree-sitter/PageRank with a token-budgeted binary
search [R] aider.

## 5. 16 GB-specific tactics

- **KV-cache quantization** on the MLX side (`--kv-bits`, `--quantized-kv-start`,
  `--max-kv-size`) — 2–4× more context for the same RAM **[L]**. The CLI must
  *report and respect* the served `num_ctx`, never assume a window.
- **Model tiering** — route cheap turns (title, summary, rerank, classify) to a
  3–4B model; keep an 8B for tool-calling; never load a 14B alongside a large KV
  cache.
- **Pre-warmed system prefix** **[L]** so the first user token does not pay full
  prefill.
- **Disk-backed spill** for elided tool output, so effective context can exceed
  RAM without OOM.

## 8. Non-goals / unknowns

- **Not** building a new agent loop — `AgentController` is reused.
- **Not** relying on an opencode "context add/ls/forget" feature — that premise
  was wrong in the prior research **[R]**.
- The unterminated **[R]**/**[L]** constants and literals (aider/cline/pi/opencode
  values, external numbers) have **not** been re-verified in this doc. Re-check
  against source before they land in code or comments.
